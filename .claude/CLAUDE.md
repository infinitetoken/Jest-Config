# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

# @infinitetoken/jest-config

Shared Jest configuration for InfiniteToken TypeScript packages. Part of the `@infinitetoken` shared tooling scope, alongside `@infinitetoken/eslint-config` (`../ESLint-Config`) and `@infinitetoken/tsconfig` (`../TSConfig`).

## Commands

```bash
npm run lint   # ESLint check
npm test       # Verify all presets resolve, merge, and default correctly
npm run verify     # lint + test
```

## Release

Tag-based, using npm trusted publishing (OIDC, no token required):

```bash
npm version patch   # or minor / major
git push --follow-tags
```

The `publish.yml` workflow fires on `v*` tags and runs `npm publish`.

## Presets

| Export | Use for |
| --- | --- |
| `./node` | Base preset, `testEnvironment: 'node'` — kits, Node plugins, any non-UI package |
| `./react-native` | React Native / UI **library** packages, `testEnvironment: 'jsdom'`, ts-jest; composes on `./node`, so it inherits everything below too |
| `./expo` | Expo **apps**, `preset: 'jest-expo'` (Babel-based); standalone, does NOT compose on `./node` |
| `./setup` | The shared `unhandledRejection` logger, independently resolvable |

`./node` (and therefore `./react-native`) now default `collectCoverage: true`, `testTimeout: 10000`, `verbose: true`, `maxWorkers: '50%'`, `collectCoverageFrom: ['src/**/*.{ts,tsx}', '!src/**/*.d.ts', '!src/index.ts']`, `coverageDirectory: 'coverage'`, `coverageReporters: ['text', 'lcov', 'html']`, and `coverageThreshold` at 70%/70%/70%/70% globally — every consumer in the fleet was hand-duplicating these exact values before this was added, confirmed by diffing across the repos migrated so far.

**`maxWorkers: '50%'` (`src/utils/workerDefaults.cjs`, shared by `./node` and `./expo` exactly like `coverageDefaults.cjs` — no apps-vs-libraries split here, unlike coverage below).** Jest's own default, `numCpus - 1` heavy worker processes, assumes every logical core is an equally fast, otherwise-idle lane. Neither holds on a real fleet dev machine: confirmed via `sysctl hw.perflevel0.physicalcpu hw.perflevel1.physicalcpu` on a real machine that Apple Silicon's "8 logical CPUs" can be 6 performance + 2 efficiency cores, not 8 equal ones, and a dev machine is never idle outside Jest — an IDE, other Claude Code sessions, and often a native build (Xcode/EAS) are real, simultaneous, CPU-hungry neighbors, confirmed directly rather than assumed (a load average as high as 424 was observed on an 8-core machine mid-investigation, driven by exactly this combination). This matters more than "tests run a bit slower": a worker that isn't rescheduled promptly still has to finish its real (non-fake) timers and effects inside Jest's fixed per-test timeout, so oversubscription produces outright timeout failures, not just a slower pass. Verified directly against a real consuming app (Hangman, `./expo` preset, 30 suites / 391 tests) rather than a scratch fixture: at Jest's uncapped default (7 workers on a 6-performance-core M1 Pro), 6-14 of the heaviest suites (the ones rendering the largest component trees) flaked with bare `Exceeded timeout of 5000ms` failures — no assertion detail, meaning the code was never wrong, it just didn't get scheduled in time. Two structurally-identical real-timer hook tests in that repo (`usePopSound.test.ts`, `useClickSound.test.ts` — same mock setup, same fixed 10ms/0ms real `setTimeout` waits), run in the very same invocation, took 22s and 744s respectively: same code, same waits, purely different scheduling luck. Capping `maxWorkers` at 4 (50% of 8) made that exact same suite pass 391/391 — and finish in 21s, actually *faster* than the uncapped default's 62s on an otherwise-idle machine, because nothing was left idle mid-test waiting to be rescheduled. A percentage, not a fixed number, specifically because this package runs across whatever machine each fleet developer actually has — the underlying problem (real dev machines always have competing CPU demand) applies regardless of core count, so the default should scale with the machine rather than bake in one Mac's number. Still fully overridable via `overrides.maxWorkers` (e.g. a CI runner where a fixed number fits better than a percentage). Unlike `collectCoverage`/`coverageThreshold` below, this is spread into `./expo` wholesale, not picked apart — there's no apps-vs-libraries exception for it, since oversubscription starves a heavy app-screen render exactly the same way it starves a heavy library test.

**`collectCoverage: true` is what actually makes `coverageThreshold` real.** For a long stretch of the fleet migration, `coverageThreshold` existed in every consumer's `jest.config.cjs` (via this factory) but enforced nothing anywhere: `coverageThreshold` only does anything when Jest is actually collecting coverage, and every consumer's `test` script was bare `jest` (no `--coverage` flag), with `collectCoverage` never set in the config either — confirmed by checking the fleet's shared reusable CI workflow (`infinitetoken/Workflows`' `npm-ci.yml`) too, which just runs `npm run verify` with no coverage flag added at that layer. So the threshold was pure documentation, checked only if a human happened to run `npx jest --coverage` by hand. Setting `collectCoverage: true` here makes plain `jest` — and therefore `npm test`/`npm run verify`/CI, unchanged — actually enforce it, fleet-wide, the moment a consumer is on this version, with zero per-repo script changes needed. Verified directly: a scratch project on this factory with 1/3 functions tested exits `1` under bare `npx jest` (confirmed via the real process exit code, not through a pipe — piping through `tail` silently discards the real exit code and reports `tail`'s instead, a mistake caught happening for real during this same verification). A consumer that wants a fast, uninstrumented watch loop should override just that one script invocation (e.g. `"test:watch": "jest --watchAll --coverage=false"`) rather than disabling the default — the point is that enforcement is now the default everywhere it isn't explicitly opted out of, not something each repo has to remember to turn on. `.tsx` is included unconditionally, not just for `./react-native` consumers: for a pure-`.ts` package the glob matches exactly the same files it always did (a strict superset, never a behavior change), while every React/React Native package in the fleet has real `.tsx` source this would otherwise silently exclude from coverage measurement entirely — previously every such repo had to hand-add the identical `overrides.collectCoverageFrom` override just to widen the glob, confirmed across every `@rific`/`@tastic` component-library repo migrated so far, so the "override" was never actually expressing a real per-repo deviation. There's no `'!**/__tests__/**'` entry either — verified empirically (a from-scratch plain-JS Jest project, no ts-jest/tsconfig involved) that Jest already excludes any file matched by `testMatch` from coverage collection regardless of what `collectCoverageFrom`'s glob matches, so the entry never did anything; it was carried forward from an earlier, unverified assumption about how Jest's coverage collection works. A package below the 70% threshold in any dimension needs an explicit `overrides.coverageThreshold` at a value it actually meets, with a comment explaining why, rather than letting a migration silently start failing CI on coverage.

**`./react-native` defaults `testEnvironmentOptions: { customExportConditions: [] }`.** `jest-environment-jsdom` hardcodes `customExportConditions` to `['browser']` as its own built-in default (confirmed directly in `@jest/environment-jsdom-abstract`'s installed source), for a reason unrelated to Metro — it's just labeling "this environment provides browser-like globals." Several fleet packages (`@tastic/core`, `@tastic/profile`, `@tastic/hud`, confirmed by grepping every `package.json` in the fleet for a `"browser"` key in `exports["."]`) define a real `"browser"` condition pointing at raw, untranspiled source (`./src/index.ts`), deliberately, for Metro's Expo Web target — same reasoning as their `"react-native"` condition: Metro transforms raw source itself, so pointing it at pre-built `dist/` would be redundant at best. jsdom's default activates that same condition for an unrelated reason, with no awareness that this specific condition assumes a bundler that does its own transforming. Jest does not transform `node_modules` by default, so it hands the raw `.ts` straight to Node's CJS loader, which fails with `Must use import to load ES Module`. Setting this to `[]` doesn't add anything — it fully replaces jsdom's hardcoded default with nothing (confirmed in the same source: any value present in `testEnvironmentOptions.customExportConditions`, even an empty array, replaces the built-in `['browser']` rather than merging with it), so resolution falls through to `require`/`import` — the real built `dist/` output. A no-op for any consumer that never resolves a `"browser"`-conditioned package for real, which is most of the fleet.

Discovered independently twice before being centralized here: two sibling repos (`React-Native-Game-Input`, `React-Native-Game-Physics`, both depending on `@tastic/core`) each added the identical local override with slightly different syntax (`['']` vs `[]` — functionally equivalent, since neither matches a real condition name, but only one is the idiomatic way to say "no custom conditions"), and a third (`React-Native-Hud`) sidestepped the issue entirely by mocking `@tastic/core` away rather than touching the jsdom default, with an explicit comment reasoning that a project-wide default change felt too big "just for one two-line function." Once the pattern showed up a third time across only three total occurrences, centralizing here made more sense than leaving it to keep getting independently rediscovered.

`testEnvironmentOptions` had to be added as a real, explicitly-named, destructured option in `node.cjs` itself, not just passed through from `react-native.cjs` — `node.cjs` only forwards the specific option keys it destructures (plus whatever's inside `overrides`, spread wholesale); any other key passed into its factory call is silently dropped, not merged. This was caught by a real assertion failure (`actual: undefined`) when first adding this default, not just written correctly on the first attempt — worth remembering as the pattern for any future top-level default a variant preset like `./react-native` wants to add: it must be a named option in the base `node.cjs`, or it silently never reaches the returned config at all.

All three factories are functions, not static objects/arrays like `eslint-config`'s exports — Jest's `moduleNameMapper` and the inline ts-jest `tsconfig` fragment don't compose via shallow spread, and two `tsconfig` dialects exist across the fleet (a file path string vs. an inline object), so a function is needed to merge nested defaults and branch on which dialect it's given.

**Libraries vs. apps is a real architectural split, but narrower than first documented here — `./expo` stays standalone because of `preset`/`transform` ownership, not because manual `__mocks__/` mocking is incompatible with `jest-expo`.** The original version of this note claimed Expo apps' Babel-based transform "has nothing in common with" the library presets' `ts-jest` + hand-written `src/__mocks__/*` strategy, and that there was "no meaningful way to compose these two strategies." That overstated it: Jest's `__mocks__/`-adjacent-to-`node_modules` manual-mock pickup is a resolver-level feature, independent of transform — confirmed directly against a real consuming app migrating off `jest.setup.ts`-inline `jest.mock()` calls (`jest.isMockFunction()` asserted `true` on an export with zero `jest.mock()` call anywhere, both at repo-root `__mocks__/` and, once `roots` below existed, at `src/__mocks__/`). The real reason `./expo` doesn't compose on `./node` is that `jest-expo` owns `preset`/`transform` outright for its own Babel pipeline, which doesn't layer under `node.cjs`'s explicit `ts-jest` transform — an actual conflict, not a mocking-strategy one. `./expo` also does NOT auto-inject the shared `setup.cjs` logger the way the library presets do: every app's own `jest.setup.ts` already installs its own `unhandledRejection`/`uncaughtException` handling plus substantial native-module mocks, so injecting a second logger would be pure duplication, not a gap worth filling. Its `paths`/`aliasCatchAll` options generate the `@/segment` → `src/segment` moduleNameMapper pattern every surveyed app already used by hand (with a `moduleNameMapper` escape hatch for one-off exceptions, e.g. an alias pointing at a single file rather than a directory) — now mostly superseded by the tsconfig-derived alias below, but kept for an alias not declared in `tsconfig.json`, or one that needs to differ from it.

**`roots` defaults to `['<rootDir>/src']`, same as `node.cjs`.** Every Expo app surveyed so far (Swirlio, LightCycles, BoxHockey) originally hand-mocked native modules inline in `jest.setup.ts` via `jest.mock(module, factory)` — consistent across all three, but never because the alternative didn't work; nobody had tried it. Once confirmed that manual `__mocks__/` mocking works fine under `jest-expo` (see above), `roots` was added — without it, Jest's default `roots` is the project root, so an automatically-picked-up manual mock would need to live at root `__mocks__/`, sitting exactly as far from `src/__tests__/` as `jest.setup.ts` already does. Scoping `roots` to `src/` makes `src/__mocks__/` the pickup location instead — next to `src/__tests__/`, matching the library presets' own convention exactly, and one file per mock instead of one growing `jest.setup.ts`. A real side benefit, not the motivation: since `.claude/worktrees/` lives outside `src/`, a scoped `roots` also means Jest's haste map never crawls an active Claude Code worktree there, which previously required a per-app `overrides.modulePathIgnorePatterns` workaround (see LightCycles' own CLAUDE.md) when an app had one checked out. Still overridable via `overrides.roots` for an app that genuinely needs a broader scope.

**`jest.setup.ts` is now auto-detected (`fs.existsSync` against `process.cwd()`, same technique `readPathAliasMapper()` already used for `tsconfig.json`), not something every consumer passes by hand.** All three surveyed apps called `createExpoJestConfig({ setupFilesAfterEnv: ['./jest.setup.ts'] })` — identical boilerplate every time, since every real Expo app has one. `setupFilesAfterEnv` now means "additional setup files beyond jest.setup.ts" and defaults to `[]`; the detected file (if present) is always prepended first, matching the order every surveyed app already used by hand for the gesture-handler setup file after it. Guards against the one real failure mode: an app that hasn't yet deleted its own now-redundant `setupFilesAfterEnv: ['./jest.setup.ts']` would otherwise get the file listed twice under two different path spellings (`'./jest.setup.ts'` vs the detected `'<rootDir>/jest.setup.ts'`) — a plain string-equality dedupe wouldn't catch that, so both entries are resolved to absolute paths for comparison before an explicit entry matching the detected file is filtered out. This is exactly the "leaving both in place double-registers the same `process.on` handler" pitfall this file already documents for `setup.cjs` migrations, just self-inflicted this time instead of left over from a pre-migration file. Consumers should remove their own explicit `setupFilesAfterEnv: ['./jest.setup.ts']` line once on this version — not required (the dedupe covers it), but it's dead weight once the file is picked up automatically.

**Detection was broadened to check `jest.setup.js`/`.mjs`/`.cjs`/`.ts`, in that priority order — matching the same four extensions Jest itself tries for `jest.config.*`, deliberately not just `.ts`.** `jest.setup.ts` genuinely isn't broken the way `jest.config.ts` is: `setupFilesAfterEnv` entries go through Jest's own test transform (Babel, under `jest-expo`), which handles `.ts` fine — confirmed directly, every real app's `jest.setup.ts` worked untouched. `.cjs` also works (confirmed too — a `.cjs` `setupFilesAfterEnv` entry is loaded via plain `require()`, skipping transform entirely, so real TypeScript syntax throws a hard `SyntaxError`; the content has to actually be plain JS, not just a renamed `.ts` file). Since both genuinely work, the detector doesn't pick a side — it takes whichever extension the app actually has. In practice, though, all three real apps (Swirlio, LightCycles, BoxHockey) ended up on `jest.setup.cjs` anyway, once `.cjs` and `.ts` stopped being a live technical question and became just "why does this one app-authored config file use a different extension than every other app-authored config file for no remaining reason" — the same question that converted `jest.config.ts`, applied one file later. `jest.setup.ts`'s content had also shrunk to thin boilerplate by then (the substantial part — mock factories — had already moved into typed `src/__mocks__/*.ts` files), so there was little type-checking left to give up.

**Known-offender subpath mocks (`src/utils/knownSubpathMocks.cjs` + `src/configs/registerKnownSubpathMocks.cjs`, wired into `./expo`'s `setupFiles`, gated behind the `knownSubpathMocks` option, default `true`).** Jest's manual `src/__mocks__/`-adjacent-to-`node_modules` auto-pickup (`registerSubpathMocks.cjs`, wired in via `autoMockSubpaths.cjs` — see that file's own comment) only ever matches a bare package specifier (`redux-persist`, `@scope/pkg`), never a deep subpath import (`redux-persist/integration/react`, `@scope/pkg/sub`) — a real Jest resolver limitation (manual-mock lookup keys purely off package identity, confirmed by reading Jest's own resolution source), not a gap in this package's own walk logic. Every app in the fleet that imports one of two specific subpaths directly — `@rific/feedback-press/audio` (a real, non-trivial native audio-pooling module) and `@shopify/react-native-skia/src/web` (fetches and initializes a WASM build of Skia at runtime, with no guard against running outside a real browser) — has independently rediscovered that gap and hand-registered an identical `jest.mock()` call in its own `jest.setup.cjs` (confirmed against AirHockey's current `jest.setup.cjs`: the exact same stub shape, `useAudioPool: () => () => {}` and `LoadSkiaWeb: () => Promise.resolve()`). Once a subpath shows up independently across enough apps rather than being ported forward copy-paste, it clears the same "centralize it" bar this file already applies to `testEnvironmentOptions.customExportConditions` above — these two just clear it for the manual-mock-subpath case instead of the jsdom-environment case.

`{ virtual: true }` is required on every entry, not optional, and this is the one place this default had to diverge from simply copying an app's existing `jest.mock()` call verbatim: confirmed directly against a real Jest run that `jest.mock(specifier, factory)` **without** `virtual: true` still fully resolves the real module before ever consulting the factory, throwing a hard `Cannot find module '...' — To mock a module that does not exist on disk, pass {virtual: true}` test-suite-load failure (not a graceful no-op) the moment the specifier isn't actually installed. Neither `@rific/feedback-press` nor `@shopify/react-native-skia` is a real dependency of every app in the fleet, so defaulting this to `true` fleet-wide would otherwise crash every suite in any app that depends on neither package the instant it upgraded onto this version. `virtual: true` removes the resolution requirement entirely while continuing to work identically for an app that *does* have the real package installed (confirmed both ways in the same scratch test) — so `knownSubpathMocks: true` is safe as an on-by-default for the whole fleet, not just the subset of apps that happen to need either stub.

Registered via `jest.mock()` calls inside a plain `setupFiles` module, the exact same mechanism `autoMockSubpaths.cjs` already uses and that file's own comment already confirms works (`jest.isMockFunction()` asserted `true` with zero `jest.mock()` call in the test file itself) — no hoisting concerns, since hoisting only matters for moving a `jest.mock()` call above an ES `import` statement in a test file, and a plain CJS setup module has no imports to hoist above. `registerKnownSubpathMocks.cjs` is listed *after* `autoMockSubpaths.cjs` in `setupFiles`, deliberately: an app migrating onto this version that hasn't yet deleted its own now-redundant `src/__mocks__/@rific/feedback-press/audio.ts` (or the skia one) would otherwise have that local file's `jest.mock()` registration (fired by the `autoMockSubpaths.cjs` walk) silently overwritten anyway once this default engages, since whichever `jest.mock()` call for a given specifier runs last wins the registry — ordering it last just makes that the intended outcome instead of an accident, exactly the same "now-redundant local fix superseded by the shared default, drop it" story as the `.mjs` transform gap this file documents at the top. An app that genuinely wants a *different* stub for one of these two specifiers doesn't need `knownSubpathMocks: false` at all — its own `jest.setup.cjs` `jest.mock()` call runs later still (`setupFiles` always finishes before `setupFilesAfterEnv`), so it naturally wins last regardless.

**Bug fix (2026-09-17): the `@rific/feedback-press/audio` stub only covered `useAudioPool`, not `useGatedAudioPool`.** A fleet-wide audit found AirHockey's `hooks/useGameSound.ts` re-exports `useGatedAudioPool` directly — a real gap, not a hypothetical one: any future test rendering a component that calls it would have hit real `expo-audio`/native audio APIs during a Jest run instead of the intended inert stub. Fixed by adding `useGatedAudioPool: () => () => {}` alongside the existing `useAudioPool` entry in `knownSubpathMocks.cjs` — same inert-hook shape, since a test never needs the real sound-enabled gating logic, only a safe no-op. Now `0.3.1` (patch — no API change, an existing default just covers more).

**AsyncStorage mock delegation (`src/utils/asyncStorageMock.cjs`, wired into `./expo`'s `moduleNameMapper`, gated behind the `asyncStorageMock` option, default `true`).** Two apps in the fleet mocked `@react-native-async-storage/async-storage` in genuinely incompatible ways: Snake's manual mock (`src/__mocks__/@react-native-async-storage/async-storage.ts`) has every method resolve to a no-op/null with no actual storage behind it — predictable, but no test using it can ever observe a value it just wrote — while LightCycles' current one-line manual mock (`module.exports = require('@react-native-async-storage/async-storage/jest/async-storage-mock')`) delegates to the package's own official Jest mock, a real in-memory key/value store that makes genuine write-then-reload round-trip coverage possible (confirmed live in LightCycles' `useProfiles.test.tsx` persisted-selection coverage). The official mock is strictly more capable with zero extra maintenance cost — it ships with the package itself — so this default standardizes the fleet on it rather than picking a side to reimplement.

Wired in as a `moduleNameMapper` entry, not a `src/__mocks__/` file this package ships, for a structural reason, not a style preference: Jest's manual-mock `__mocks__/` convention only ever crawls the *consuming app's* own `roots` (scoped to `<rootDir>/src` by this same preset's own `roots` default, see above) — a `__mocks__` directory living inside this package's own installed tree (`node_modules/@infinitetoken/jest-config/src/...`) is never on that crawl path, so there is no way to ship a "just gets auto-discovered" manual mock file the way an app's own local `src/__mocks__/` works. A `moduleNameMapper` entry pointing straight at the real, installed package's own jest-mock file — the same mechanism `readPathAliasMapper()` already uses to point `@/*` imports at real source — is the only way to make an app's bare-specifier `require` resolve to it by default.

Resolved via a guarded `require.resolve()`, matching `readPathAliasMapper()`'s own try/catch-returns-`{}` precedent exactly: `@react-native-async-storage/async-storage` is presumably an optional dependency for apps in the fleet that don't use any local storage at all, so this must never throw for a consumer that doesn't have it installed. Confirmed directly against this package's own repo, which has no such dependency installed anywhere on its resolution path: `createExpoJestConfig()` still builds a complete config with no `'^@react-native-async-storage/async-storage$'` key rather than throwing — the same "verified against a real absence, not just written correctly on the first attempt" bar the `testEnvironmentOptions` note above sets, not merely asserted. The positive case (the mapping actually appearing once the package genuinely is installed) is verified the same rigorous way this file's path-alias tests are: `scripts/verify-exports.cjs` drops a scratch fixture package directly into this repo's own `node_modules/@react-native-async-storage/` (cleaned up in a `finally`, mirroring the tsconfig scratch-dir tests' own cleanup discipline) rather than trusting the guarded-resolve logic on code reading alone, since `require.resolve()` walks up from `asyncStorageMock.cjs`'s own file location through parent `node_modules` directories — not `process.cwd()` the way `readPathAliasMapper()`'s tsconfig lookup does — so a `process.chdir()`-based scratch dir (the technique used for the tsconfig fixtures) would not have exercised it at all. That same walk-up-from-file-location behavior is exactly what makes this resolve correctly once installed for real: from inside `node_modules/@infinitetoken/jest-config/src/utils/`, Node's own resolution algorithm reaches a real consuming app's top-level `node_modules` the same way it already does for `jest-expo`/`ts-jest`, without this package ever needing to know the consumer's `cwd`.

Ordered before the tsconfig-derived `pathAliases`/`aliasCatchAll`/explicit `moduleNameMapper` spreads in `expo.cjs`'s own `moduleNameMapper` object, so an app that wants a different async-storage mock can still override it for free via its own `moduleNameMapper` option — no separate escape hatch needed beyond the one every other default here already has.

**Path alias auto-derivation (`src/utils/pathAliases.cjs`, shared by `./node` and `./expo`).** A repo's `tsconfig.json` `paths` (e.g. `"@/*": ["./src/*"]`) is the real source of truth for a path alias — but Jest's own module resolution doesn't read tsconfig `paths` natively, so historically every consumer had to hand-duplicate the same mapping into `jest.config.cjs` as a `moduleNameMapper`, with no guard against the two drifting apart. `readPathAliasMapper()` reads the consumer's own `<cwd>/tsconfig.json` via TypeScript's own `ts.readConfigFile` (not raw `JSON.parse` — tsconfig.json legitimately allows comments/trailing commas, and this needed to survive that) and feeds `compilerOptions.paths` through `ts-jest`'s own `pathsToModuleNameMapper`. Returns `{}` (never throws) when there's no `tsconfig.json` or no `paths` — path aliasing is opt-in per-repo, not assumed.

**The derived mapper is sorted by descending key length before being returned — this is load-bearing, not cosmetic, and was only found by testing against a real app's actual tsconfig, not the original scratch fixture.** `ts-jest`'s own `pathsToModuleNameMapper` (confirmed by reading its source directly) preserves whatever order `compilerOptions.paths` declares its keys in, with no specificity handling at all. TypeScript itself resolves paths by most-specific-match, but Jest's `moduleNameMapper` is a plain list of regexes tried in insertion order — first match wins, not most-specific-match. A tsconfig that declares a catch-all (`"@/*": ["./*"]`) before more specific segment aliases (`"@/components/*": ["./src/components/*"]`) — a real pattern found in a real consuming app's tsconfig.json, not something the original single-entry scratch fixture (`"@/*": ["./src/*"]`, no ambiguity possible) could ever have caught — produced a mapper where the catch-all silently won for every import, resolving everything to the project root instead of `src/`, with real test suites failing "Could not locate module" as a result. Sorting by descending key length (a longer regex has more literal path-segment characters before its wildcard, so it's the more specific pattern) fixes this the same way most path-alias resolvers handle overlapping prefixes. Lives in its own file rather than inline in `node.cjs` specifically because `expo.cjs` needed it too and the two presets don't compose (see above) — this was added mid-session when a consumer pointed out that `expo.cjs`'s existing `paths`/`aliasCatchAll` options still required manually re-declaring segments already present in `tsconfig.json`, right as the same duplication was being deliberately removed from a real consumer's (`TermKit`) `node.cjs` usage. `typescript` is a required peerDependency as of this change (previously only an implicit transitive need via `ts-jest`'s own peer) — this factory now calls into it directly, not just referencing it by string for `ts-jest` to consume later.

Empirically verified before removing the pre-existing manual `moduleNameMapper` from any real consumer: derive the mapper via a scratch `tsconfig.json` + `process.chdir()`, confirm it's byte-identical to the hand-written version (`{"^@/(.*)$": "<rootDir>/src/$1"}` for `TermKit`'s alias), confirm the full real test suite (127 real `@/` imports across 31 suites / 619 tests) still passes with the manual override removed and only the derived one in place.

**Bare `.` (an alias for `./node`) existed briefly this session, then was removed outright, not deprecated.** The original reasoning for keeping it alongside `./node` — "removing it would be a breaking change for consumers already migrated onto it" — turned out to be untested speculation, not a checked fact: a fleet-wide grep for `require('@infinitetoken/jest-config')` (bare, no subpath) came back with zero matches, while nine repos were already on the explicit `require('@infinitetoken/jest-config/node')`. There was no real consumer to be backwards-compatible *for* — this whole package was built this same session, so "existing consumers" meant same-session, still-uncommitted migration work, not an external installed base. Once checked, keeping the alias was pure unused surface area with a misleading justification attached; removed rather than left as a hedge against a risk that didn't exist.

`ts-jest` is a bundled `dependency` (one authoritative version for the fleet, only ever referenced by string inside the generated config — same role as `typescript-eslint` in eslint-config). `jest` is a peerDependency declared as `^29.7.0 || ^30.0.0` — the union of what the library presets need (`^30`) and what `jest-expo` pins apps to (`~29.7`), since a single package can't declare a different peer range per subpath. `jest-environment-jsdom` (optional, `/react-native` only) and `jest-expo` (optional, `/expo` only) round out the peers — both stay peer-only rather than bundled, since each must track the consumer's own installed version exactly (an Expo app's `jest-expo` version is pinned to its Expo SDK).

Repo-specific overrides (a different `moduleNameMapper`, extra setup files, ESM-mode ts-jest transform options, a genuine coverage deviation) stay local, passed as options to the factory — never add per-repo logic here. This is narrower than it used to be: coverage config specifically (`coverageThreshold`, `coverageDirectory`, `coverageReporters`, `collectCoverageFrom`) and `testTimeout`/`verbose` are now factory defaults (see Presets above), not something every consumer declares — only a genuine deviation from those defaults belongs in a consumer's `overrides`.

**When migrating a repo onto this package, always read its `jest.setup.*` file in full first.** The shared `setup.cjs` this factory auto-injects is exactly the `unhandledRejection` logger below — many repos across the fleet still have a local copy of that exact pattern predating this package. If a repo's setup file's entire content is just that, delete the file outright and drop the `setupFilesAfterEnv` line pointing at it. If it has other real content mixed in (native-module mocks, a `__DEV__` shim, etc.), keep the file but strip only the redundant handler lines — leaving both in place double-registers the same `process.on` handler (not a crash, just double-logs on a rejection, but it's dead weight). Confirmed present in ~26+ repos fleet-wide as of the last full sweep.

**Local self-testing cost:** `scripts/verify-exports.cjs` actually invokes `createExpoJestConfig()`, which calls into `jest-expo`'s real `resolveBabelOptions` → `babel-preset-expo` → `expo/config` chain. That pulled `expo`, `jest-expo`, `babel-preset-expo`, and `babel-jest` in as devDependencies (~1200 packages) purely so this repo's own CI can exercise that path — none of it ships (the `files` whitelist only publishes `src/**`), and real consumers already have this exact weight installed via their own Expo app, so it costs nothing downstream. It does mean this repo's own `npm ci` is heavier than `eslint-config`'s or `tsconfig`'s.

**Type declarations (`node.d.ts`, `react-native.d.ts`, `expo.d.ts`), added alongside each `.cjs` factory.** Originally added because every real Expo app's `jest.config.ts` used real `import`/`export default` syntax (see README's "Why `.cjs`, not `.ts`"), so `tsc` type-checked it directly — with no `.d.ts` published, `import createExpoJestConfig from '@infinitetoken/jest-config/expo'` failed with `TS7016` ("implicitly has an 'any' type") the moment a consumer's tsconfig turned on `noImplicitAny`/`strict` (which every app does the moment it migrates onto `@infinitetoken/tsconfig`, whose base preset — unlike `expo/tsconfig.base` — actually sets `strict`). Found by migrating a real app (Crumby), not written speculatively. Now that every real consumer (Expo apps included) is on plain `jest.config.cjs`, `tsc` never actually type-checks any consumer's jest config file directly (`.cjs` isn't in any app's tsconfig `include`) — the `.d.ts` files are kept anyway for editor/IDE hover-and-autocomplete via the `exports` map's `types` condition, and because `node.d.ts`/`react-native.d.ts` predate this and library packages were never the reason they were needed in the first place. Each `.d.ts` declares a `CreateJestConfigOptions`/`CreateExpoJestConfigOptions` interface matching that factory's own JSDoc, plus `declare function ...(options?): Config` using `import type {Config} from 'jest'`, exported via `export default` (not `export =`) since every real consumer already imports with default-import syntax and this fleet's base tsconfig sets `esModuleInterop: true`, which makes that interop work correctly at runtime for a plain `module.exports = fn` CJS module. `setup.cjs` has no `.d.ts` — nothing imports it via `import` syntax, it's only ever referenced as a bare path string inside a `setupFilesAfterEnv` array, already typed `string[]`.

Wired into `package.json`'s `exports` map via a `types` condition on each subpath (`"./expo": {"types": "./src/configs/expo.d.ts", "default": "./src/configs/expo.cjs"}`, etc.) rather than relying on TypeScript's implicit same-named-sibling `.d.ts` lookup — that implicit rule pairs `.d.cts` with `.cjs` specifically, not plain `.d.ts`, and an explicit `types` condition works regardless of extension-pairing rules. Verified against a real consumer (Crumby) via the same node_modules-overlay technique used elsewhere this session, not just asserted.

Adding real `.ts` files (even just `.d.ts`) to a `.cjs`-only package surfaces the same "type-aware ESLint needs a real root `tsconfig.json`" wrinkle `@infinitetoken/tsconfig`'s own CLAUDE.md documents for its `src/` reorg — this repo never had one before since it had nothing for the type-aware parser to project against. Fixed the same way: a minimal, unpublished root `tsconfig.json` (not in `files`) whose only job is satisfying that local lint convention.

## File layout

Everything lives under `src/`, not repo root — purely a physical/repo-tidiness move, not an API change, mirroring the same move in `ESLint-Config`. Within `src/`, a second-level split separates the two different KINDS of file: `src/configs/` holds the four files with their own public `exports` entry (`node.cjs`, `react-native.cjs`, `expo.cjs`, `setup.cjs`) — plus `autoMockSubpaths.cjs` and `registerKnownSubpathMocks.cjs`, which don't have a public `exports` entry of their own but still live here rather than in `src/utils/`, because each needs its own real, `require.resolve()`-able file path to hand to Jest's `setupFiles` array (an array of file paths Jest loads directly, not a value a consumer or another config file ever imports); `src/utils/` holds internal-only helper code with no public export AND no need for its own resolvable path — code that's `require()`'d directly by another file in this package, never referenced by path (`pathAliases.cjs`, `coverageDefaults.cjs`, `workerDefaults.cjs`, `registerSubpathMocks.cjs`, `knownSubpathMocks.cjs`, and `asyncStorageMock.cjs`, each required by name from whichever `configs/*.cjs` file(s) need it). `coverageDefaults.cjs` holds `{ collectCoverage: true, coverageDirectory, coverageReporters, coverageThreshold }` — same reasoning as `pathAliases.cjs` for living in a shared file (`expo.cjs` doesn't compose on `node.cjs`, so anything both need has to live somewhere both can reach, rather than being independently copy-pasted where the two copies could drift, exactly what happened to the `^_`-prefix ESLint pattern before it was centralized — see `ESLint-Config`'s own CLAUDE.md for that story) — but `expo.cjs` only takes `coverageDirectory`/`coverageReporters` from it, NOT `collectCoverage`/`coverageThreshold`. Verified directly against a real consuming app (not a scratch fixture) that enforcing those two by default would be wrong for `/expo` specifically: real coverage came back under 12% on every metric for the fleet's actual reference app, nowhere near the 70% floor that's correctly enforced for library packages — apps and libraries aren't the same category of consumer for this, and forcing library-level enforcement onto apps by default would break `npm test` immediately on upgrade. See `expo.cjs`'s own comment for the full reasoning; `coverageDirectory`/`coverageReporters` are harmless metadata either way (inert unless coverage collection is ever turned on), so those two stay shared. `collectCoverageFrom` is deliberately NOT in this shared file — it stays a per-preset literal since the two presets' conventions genuinely differ (`node.cjs` excludes `src/index.ts` as a library barrel file; `expo.cjs` has no such convention for an app's entry point). This split was added specifically when `pathAliases.cjs` arrived — one internal-only file sitting flat alongside four public preset files was exactly the ambiguity it exists to avoid ("is this one of the exported presets or not?"). No API change here either: every `exports` entry in `package.json` still maps to the same public subpath as before (`./node`, `./react-native`, `./expo`, `./setup`); only the right-hand-side file path changed, e.g. `"./expo": "./src/configs/expo.cjs"`. No consumer sees or needs to know about `src/configs/`/`src/utils/` — `require('@infinitetoken/jest-config/expo')` resolves exactly the same before and after (verified directly against the resolver, not just asserted). Unlike `TSConfig`'s `tsup/` directory, this doesn't touch the *public* subpath — nesting `./jest/expo` here would just repeat this package's own name for no reason; see `TSConfig`'s CLAUDE.md for why that distinction matters.

`node.cjs` was named `index.cjs` until the bare `.` alias (see above) was removed — once `./node` was the *only* name for that file, "index" stopped meaning anything (every other file already matches its subpath exactly: `react-native.cjs` ↔ `./react-native`, `expo.cjs` ↔ `./expo`, `setup.cjs` ↔ `./setup`). Caught immediately, so renamed too rather than left as the one inconsistent filename. `ESLint-Config`'s `index.cjs` is a different case, not renamed: it's still genuinely the unnamed bare `.` default there — nothing else names it — so "index" is the correct word for it, the same way a package's own `index.js` conventionally means "what you get from the bare specifier."
